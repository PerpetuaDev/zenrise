# Tours CMS module — setup

Tours are generated straight from the client's Bokun account. There is no
microCMS `tours` API and none is planned — Bokun is the single source of
truth for tour content, pricing and availability.

## Build

    python3 cms/build-tours.py                  # --source bokun (default): live fetch
    python3 cms/build-tours.py --source cache    # offline, from the committed cache
    python3 cms/build-tours.py --source bokun    # same as the default, spelled out
    python3 cms/build-tours.py --live            # alias for --source bokun

`--source bokun` fetches live via `cms/bokun_client.py` (a signed REST client)
and `cms/bokun_source.py`/`cms/tours_build_source.py` (the adapter that shapes
Bokun's product + availability responses into tour records). A failed Bokun
fetch falls back to the committed `cms/tours-cache.json` automatically, so a
Bokun outage never empties the tours pages; with no cache at all the build
fails loudly. `--source cache` skips the network outright and is the
deterministic choice for local iteration or CI.

Outputs: `tour-<slug>.html` per allowlisted product (full detail once
`priceRows` and both ledes exist, otherwise the "in preparation" layout), the
card grid in `tours.html`, the homepage tiles in `index.html` (both between
`CMS:tours-grid` / `CMS:home-tours` markers), a `go/<slug>/` redirect stub per
tour, and each tour's JSON-LD + meta tags. Per-tour bilingual copy travels in
each page's `ZENRISE_CMS_DICT`, not in `lang.js`.

## When it runs

`.github/workflows/build-tours.yml`, hourly at `:00`, plus manual dispatch.
Bokun cannot call a webhook at us, so the schedule is the only automatic path —
a change made in the Bokun panel reaches the site within the hour, not
instantly. GitHub's cron is best-effort and skips under load, so treat the hour
as a floor rather than a guarantee; nothing is lost when a run is skipped,
since the next rebuild picks up every change since the last one.

It runs with `--require-live`. Without that flag a credentials failure would
rebuild from the committed cache, produce no diff, and report "no changes to
publish" — a green tick on a job that published nothing.

Offset from `build-news.yml` at `:30` because both push to `main`.

## The product list

`cms/tours-config.json` drives which Bokun products become pages:

- `allowlist` — Bokun product IDs to publish as Zenrise tours.
- `otaDenylist` — OTA-only products explicitly excluded (never published here).
- `corrections` — one-off text fixes applied to Bokun's descriptions during
  cleanup (typos, stray spacing from their editor).
- `tours[<productId>]` — per-product overrides: `slug`, `number`, `area`,
  `length`, `themes`, `jaReviewed`, and `widgets` (booking-widget path per
  language, e.g. `{"en": "<channelUUID>/experience-calendar/<productId>"}`).

`cms/tours-cache.json` is the outage floor described above — a committed
snapshot of the last good Bokun fetch, in the same shape `bokun_source.py`
produces. It is regenerated by a live build; don't hand-edit it.

## What's still open

Client-side, not code:

- **No tour has `jaReviewed: true`.** The Japanese copy Bokun returns has never
  had a native pass, on any of the ten. This has been outstanding since the
  four-tour catalogue and is the oldest open item here.
- **Six of ten have no English booking widget.** `widgets.en` is set for
  ikebana, candle-making, zen-journey and swordsmithing only; the rest need the
  widget configured on Bokun's side before an entry can be added to
  `tours-config.json`.

Pricing is no longer an issue — all ten products carry `priceRows`, so none of
them render in the "in preparation" layout any more.

The client-facing guide to all of this is `Zenrise ツアー追加ガイド（日本語版）`
(2026-08-28), which is not in this repo. Two of its instructions have since been
overtaken and need amending before it is handed on:

- It says the first uploaded photo becomes the page banner and card image. Since
  `d639a26` the cover comes from Bokun's `keyPhoto` — the hero pick — falling
  back to `photos[0]` only when that is unset. "Put your best photo first" is no
  longer the instruction; "set the key photo" is.
- It lists the areas as Kamakura, Enoshima and Yokohama. Tokyo is live as well
  (`tours_area_tokyo`, 東京), and is the area of tour 07. Its troubleshooting
  step 10 asks the reader to check the city is one of the original three, which
  would send them looking for a fault that isn't there.

It also tells the reader to ask us for a manual rebuild or a look at the build
log. Both become wrong at handover: whoever owns the repo can dispatch
`build-tours.yml` and read its logs themselves.
